# ADR-0011 — VS-01a Artist identity and persistence

**Status: accepted on 2026-10-04 for VS-01a.** This decision is intentionally bounded to the fixture-first Artist slice and does not activate live provider ingestion, public API exposure or production deployment.

## Context
VS-01a must prove that provider-shaped Artist evidence can be admitted into SongChart without making provider identity, display names or slugs canonical identity. The MVP charter already requires stable SongChart IDs distinct from provider IDs and forbids name-only merge decisions. The implementation additionally needs deterministic URL and idempotency rules before schema and application code are introduced.

## Decision
1. SongChart Artist canonical IDs use ULID values generated by SongChart.
2. Public Artist URLs use `/artists/{songchart_id}/{slug?}`. The SongChart ID is authoritative; the slug is presentation metadata and stale or missing slugs redirect to the current canonical URL.
3. External identity uniqueness is `(provider, entity_type, external_id)`. Artist names are never identity keys.
4. VS-01a stores one canonical display name plus the source/provider name as evidence. Alias/history modelling is deferred.
5. Artist type and country are nullable. Unknown values remain unknown and are never inferred from name or other weak evidence.
6. VS-01a stores normalized provenance metadata and stable external identity, not raw HTTP payloads. Raw provider evidence retention remains a VS-01b provider-policy decision.
7. Re-importing the same external identity reconciles the same canonical Artist; it never creates a second Artist solely because other display metadata changed.
8. Slugs are derived from the canonical display name using the framework transliteration-safe slugger with a deterministic fallback. Slug changes never change canonical identity.

## Persistence shape
- `artists`: SongChart-owned canonical Artist row keyed by ULID.
- `external_identities`: provider evidence linked to an Artist, with a database unique constraint over provider/entity type/external ID.
- PostgreSQL remains the intended canonical runtime authority; test environments may exercise the same migrations against the repository test database.

## Consequences
- Two Artists may legitimately share the same display name when they have different external identities.
- Provider IDs are retrievable provenance but cannot be used as SongChart primary keys.
- Renames can update display name and slug without breaking identity.
- Merge/split history, aliases, localized names, live MusicBrainz HTTP behavior and raw-evidence retention require later bounded decisions.

## Verification
VS-01a acceptance requires unit normalization tests, database idempotency/same-name distinction tests, canonical URL tests, responsive rendered Artist evidence and exact-SHA CI before merge.
